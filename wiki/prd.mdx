## Overview

Keysy is a simple, AI-assisted secret manager for local development and deployed services, with optional notes and expiration reminders.

## Problem

As secrets become shared across services, developers struggle to identify which access policies need updating and verify that permissions remain correct. Existing tools make these routine changes too complex.

## Users

The Owner, Admins, and Developers are an org’s members.

- **Owner:** One per org. Has every Admin ability, and is the only member who can rename or delete the org or transfer the Owner role.
- **Admins:** Manage Developers and their scopes, and can promote Developers to Admin. Have full access to every secret, policy, and service. Cannot change or remove Admins or the Owner.
- **Developers:** Manage secrets, services, and policies within the scope the Owner or an Admin assigns them through policies and permission sets.
- **Services:** Retrieve authorized secrets at runtime using their own identities.

## Use cases

- **Manage members:** The Owner and Admins add Developers, set each Developer’s scope with policies and permission sets, and review access requests. The Owner can change members between Admin and Developer and remove either role. Admins can promote Developers to Admin and remove Developers. The Owner transfers the Owner role to another member.
- **Request access:** Developers see every policy and request the ones they need; the Owner or an Admin approves or declines.
- **Manage secrets:** Members create, read, update, and delete secrets within their scope through the web app or CLI, with optional notes and expiration reminders.
- **Manage service access:** Members create services and grant them read access to paths within their scope.
- **Reorganize with AI:** Members use the AI agent to move secrets within their scope, identify and update affected policies, and verify permissions.
- **Track folder versions:** Every change to a secret creates a new version of its folder. Members can view a folder’s version history, see which version each service last retrieved, and roll the folder back to a previous version.
- **Review audit logs:** Members trace changes to secrets, policies, and member access, including the actor, timestamp, and outcome. Secret values are never recorded in audit logs.
- **Access secrets locally:** Developers retrieve secrets within their scope for local development.
- **Access secrets at runtime:** Services retrieve secrets permitted by their policy.
- **Save or update secrets from the browser:** Members use the Keysy browser extension to save newly generated API keys as new secrets or update the values of existing secrets, directly from provider websites.
- **Use Keysy with coding agents:** A Keysy skill guides coding agents to retrieve or manage secrets through the CLI.

## Goals

- **Simplify secret management:** Make secret management straightforward across the web app, CLI, browser extension, and coding agents.
- **Reduce manual policy maintenance:** Help members reorganize secrets and update affected policies with AI assistance.
- **Maintain least-privilege access:** Ensure Developers can access only the secrets within their scope, and services only the secrets their policy permits.

## Success metrics

- **Setup time:** p50 and p95 time from secret creation to first authorized retrieval.
- **Atomic updates:** 100% of concurrent read/write tests return a complete folder version, with no partial or mixed-version values.
- **AI success rate:** Percentage of reorganizations completed with correct permissions and no manual fixes.
- **Access correctness:** Pass rate of role, scope, and policy permission tests.
- **API performance:** Secret retrieval p95/p99 latency, reported with QPS and sample size, and validated under sustained load.

## Scope

- **Secret management:** Create, read, update, and delete secrets, with optional notes and expiration reminders.
- **Scoped access:** The Owner manages Admins and Developers. The Owner and Admins manage Developer scopes, built from policies and reusable permission sets. Developers manage secrets, services, and policies within their scope; services retrieve only secrets their policy permits.
- **AI-assisted reorganization:** Move secrets, identify and update affected policies, and verify permissions.
- **Access channels:** Web app, CLI, browser extension for saving or updating secrets, and a skill for coding agents.
- **Version history:** View the last N previous versions of each folder, what changed in each, and when, plus each service’s last-retrieved version and time per folder. Roll a folder back to any of these versions. Older versions are permanently deleted.
- **Audit logs:** Record secret, policy, and member access changes without recording secret values.

## Non-goals

- **Full OpenBao feature parity:** Keysy focuses on secret management rather than reproducing every OpenBao capability.
- **Automatic secret rotation:** Expiration reminders do not automatically rotate or invalidate secrets.
- **Dynamic credential generation:** Keysy stores existing secrets rather than issuing temporary database or cloud credentials.
- **Unlimited version history:** Keysy keeps only the last N previous versions of each folder; older values cannot be recovered.
- **End-to-end encryption:** Keysy can decrypt secrets server-side to serve authorized members, services, and integrations.
- **Read-only members:** Every Developer can write within their scope; v0 has no read-only access level.

## User flows (v0)

1. A member creates a secret within their scope through the web app or CLI.
2. The member specifies its storage path and value, optionally adding notes and an expiration reminder.
3. The member adds the path to a service’s policy, or the Owner or an Admin adds that policy to a Developer’s scope.
4. The authorized Developer or service retrieves the secret.

## Requirements

### Members and roles

- Each org has exactly one Owner and any number of Admins and Developers. The org’s creator becomes its Owner.
- The Owner and Admins can access every path and can add Developers.
- Only the Owner can rename or delete the org or transfer the Owner role. The Owner can change members between Admin and Developer and remove either role.
- Admins can promote Developers to Admin, remove Developers, and change their scopes. Admins cannot change or remove Admins or the Owner.
- Every member can view the member list, which shows each member’s name, email, and role. Developers cannot see other members’ scopes and cannot change members.
- After a transfer, the previous Owner becomes an Admin. If the Owner is unreachable, Keysy support transfers the role after verification.
- The Owner must transfer the role or delete the org before leaving it or deleting their account. Deleting an account removes the member from every org.

### Scopes and policies

- A Developer’s scope is the policies and permission sets (named groups of policies) assigned to them. Developers can read or change secrets only within their scope.
- The Owner and Admins can remove a Developer’s policies or permission sets at any time.
- A policy path is an exact folder or a prefix ending in `/*`, never a single secret.
- Each service has exactly one policy, and each policy belongs to one service. Services retrieve only secrets their policy permits.
- Keysy keeps only each service’s latest retrieved version and time per folder.
- A Developer can change a service or its policy only if all its paths, before and after, are within their current scope.
- Developers see every policy’s name and service, but not paths outside their scope. They can request such a policy with an optional reason. The Owner and Admins are notified, and one of them approves or declines.
- Moving or deleting secrets updates every affected policy. The change is blocked if the member cannot manage one of those policies.

### Secrets and versions

- Notes and expiration reminders are optional.
- A secret value can span multiple lines. A text file, such as a `.p8` key or service account JSON, loads as one value. Binary files are not supported.
- Secrets are encrypted at rest with keys stored apart from the database, so a database leak alone cannot reveal plaintext.
- A folder holds either secrets or subfolders, never both.
- Secrets are not versioned individually. Each change creates a new version of every affected folder; a move versions both folders.
- Rolling back a folder creates a new version and keeps later versions. A folder that now holds subfolders cannot roll back to a version with secrets.
- Each folder keeps at most N previous versions.

### Audit logs

- Secret, policy, and member access changes create audit records without secret values. The version limit does not apply.
- Developers see only records for paths within their scope, and policy records only when all the policy’s paths are within it. Member, scope, and role records are visible only to the Owner and Admins.

### Account

- Members choose whether to get expiration reminders and secret update emails, and how many days ahead reminders arrive. Emails are on by default for the Owner and Admins and off for Developers. Emails skip secrets outside the member’s scope and the member’s own changes.
- Members can see every session on their account across the web app, CLI, and browser extension, and revoke any session except the current one.
