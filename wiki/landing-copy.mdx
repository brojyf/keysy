## Recommended direction

**Keysy means key + easy.** Make that promise the center of the page: managing keys
and secrets should feel straightforward. Explain AI through the work it helps you
do, rather than making AI the product's identity.

**Recommended headline:**

> Keys made easy.

**Supporting copy:**

> Manage API keys and secrets in one place, from local development to production.
> Control who can access them, and use AI to help keep them organized.

Use **Secret management for developers** above the headline to make the category
clear. The headline carries the brand; the supporting copy explains the product.

This is a copy proposal for review, not a release announcement. Feature language
below follows the [PRD](/prd); requirements do not establish current availability.
Use the prelaunch wording until the corresponding product flows are released.

Resend uses **Get started** and **Documentation**. The useful pattern is a clear
next action with an optional way to learn more. Those labels describe working
destinations; they are not a reason to add an unreleased signup or demo flow.

## Headline options

| Option | Pros | Cons | Recommendation |
| --- | --- | --- | --- |
| **Keys made easy.** | Short, memorable, and directly expresses key + easy. | “Keys” alone does not explain the full secrets category. | Preferred with the category label and supporting copy above. |
| **Secret management, made easy.** | Immediately explains the product and the promise. | More generic and less closely tied to the name. | The simplest alternative if instant category clarity matters most. |
| **Your secrets. Simply managed.** | Calm, concise, and consistent with the existing landing draft. | Communicates simplicity without making the name's meaning as explicit. | Keep if continuity with the existing design matters more. |

Choose **Keys made easy.** because it gives the name a meaning visitors can
remember. Use concrete examples below it to show what “easy” means: save a key,
assign access, retrieve it where needed, and reorganize it with assistance.

These are proposed descriptions of the intended product. Show a feature as
available only when its implementation and access path have been verified.

### Ways to use Keysy

Section heading: **Manage secrets where you work.**

| Channel | Supporting copy |
| --- | --- |
| Web app | Manage secrets, access policies, and audit logs in one workspace. |

Creation and updates require Admin access. Avoid suggesting that every user or

### Security language

Heading: **Control access to your secrets.**

> Secrets are encrypted at rest, with encryption keys stored separately from the
> database. Users and services can retrieve only what their policies allow.

This describes PRD requirements. Confirm the implementation before publishing it
as a statement about the running service. Keysy can decrypt secrets server-side;
do not describe it as end-to-end encrypted or claim that the server cannot read them.

## Voice and wording

- **Make ease concrete.** Explain the task that becomes simpler. Prefer “Save API
  keys from provider websites” over “A frictionless developer experience.”
- **Use keys for the brand and secrets for the product category.** Introduce API
  keys early; use secrets when including passwords, tokens, and other credentials.
- **Write to the developer.** Prefer short sentences with actions such as save,
  organize, retrieve, grant, and review. Use sentence case.
- **Keep AI specific.** Name the assistance: moving secrets, updating affected
  policies, and checking permissions. Avoid “AI keeps everything right.”
- **Keep simplicity compatible with control.** Explain permissions and Admin-only
  actions without suggesting that ease means unrestricted access.
- **Use evidence instead of superlatives.** Avoid “the best,” “unbreakable,”
  “enterprise-grade,” and unsupported customer, performance, or uptime claims.

## Claims that need resolution

The PRD is the scope reference; the [landing draft](https://github.com/brojyf/keysy/pull/49)
is a design reference, not proof that a capability is released.

| Topic | Editorial treatment |
| --- | --- |
| Version history | At review time, the merged PRD describes secret versions, while [PR #53](https://github.com/brojyf/keysy/pull/53) proposes folder versions and rollback. Resolve the scope before publishing detailed version or rollback copy. |
| Service retrievals | Describe the version a service **last retrieved**. A retrieval record does not establish what the service is currently running. |
| Availability | The landing draft includes redundancy and a 99.9% uptime commitment. Publish operational or SLA claims only with verified deployment evidence and defined terms. Avoid “Always available.” |
| SDKs and integrations | The design includes illustrative SDK examples. Name supported languages and show installation commands only when the packages and examples are real and verified. |
| AI data handling | The design says secret values stay out of AI conversations. Verify the complete assistant and coding-agent paths before making an absolute promise. |
| Rotation and retention | Reminders are not automatic rotation; retained history is bounded. Neither automatic rotation nor unlimited history is in the PRD scope. |

Keep the page focused on the key + easy promise. A short, specific explanation
and a working next step are enough; additional slogans should not compete with it.
